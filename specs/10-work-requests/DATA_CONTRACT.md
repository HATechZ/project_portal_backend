# Data Contract: 10 — Route-Based Work Requests

> **AUTHORITATIVE DATA CONTRACT:** The route-based concepts are additive future persistence. The pre-route V1 contract below is **HISTORICAL / PRE-ROUTE MODEL** retained for lossless read compatibility; it is not a schema blueprint for new route-based Work Requests. Exact target Prisma names/migration SQL are deferred until approved implementation design.

## Route-based persistence summary

The new model requires tenant-qualified, append-only/immutable history for route versions and route-step occurrences; one Division execution cycle per activated route occurrence; ordered Team steps per Division cycle; ordered Member steps per Team step; revisions/resume links; pair conversations/messages/attachments; and reconsideration history. `WorkRequestV1`, events, documents/versions, C1 package rows, C2 historical rows, and C3 Bid-cycle relation remain preserved. See [Route & Execution Lifecycle](ROUTE_AND_EXECUTION_LIFECYCLE.md), [Revision & Resume](REVISION_AND_RESUME.md), [Request Info Communication](REQUEST_INFO_COMMUNICATION.md), [Client Gateway & Reconsideration](CLIENT_GATEWAY_RECONSIDERATION.md), and [Migration Cutover](MIGRATION_CUTOVER.md).

Persist route position, internal-cycle position, revision pause/resume, and Client lifecycle as separate facts/projections; do not create one giant global enum or mutable status sufficient to reconstruct history. New tables require tenant-qualified FKs, RLS `USING`/`WITH CHECK`, least grants, sequence/one-active constraints, idempotency uniqueness, and append-only protections where specified.

Each route-revision resubmission records one immutable source-correction handoff with its source actor, optional note, timestamp, and ordered, exact Work Request document-version references. This handoff is distinct from normal Member-step submission history and is created before the paused requester context resumes.

The Work Request persists `originatingDivisionId` and `responsibleOriginatingDivisionLeadId` as separate tenant-qualified facts. The latter identifies the exact active DivisionLead responsibility bound at creation; it is not derivable from Division membership. A transfer requires a separate append-only responsibility-change record with predecessor, successor, actor, reason, timestamp, and correlation.

Conceptual relations are: `WorkRequestRouteVersion` (origin, responsible originating lead, predecessor/amendment and route plan); `WorkRequestRouteStep` (occurrence, ordinal, kind, Division, activation/completion); `WorkRequestDivisionCycle` (one per activated Division occurrence); `WorkRequestTeamStep` and `WorkRequestMemberStep` (parent cycle/step, ordinal, target, immutable lifecycle); `WorkRequestRevision` (classification, requester, actual source, exact contexts, resume destination, round, formal trigger); `WorkRequestConversation` (canonical pair per Work Request); `WorkRequestMessage` and immutable attachment references; and `WorkRequestReconsideration` with one request/decision history. These are conceptual names, not approved Prisma names.

## HISTORICAL / PRE-ROUTE DATA CONTRACT

### Approved unused Member-step retirement

`WorkRequestMemberStep.cancelledAt` is a nullable immutable timestamp for an unused
ordinary future step retired by an explicit repair. It is not revision state. A
cancelled step retains its ordinal, identity, member, original append event and all
audit references. Cancellation is forbidden for activated/submitted steps and for
steps referenced by a submission, revision requester/source/resume context, or the
active projection. A cancelled step can never activate or submit. Forward selection
chooses the lowest greater non-cancelled ordinal; completion ignores cancelled rows.
Revision continues to use `WorkRequestRouteRevision` and never clears or alters this
fact. The prepared `20261110010000_cancel_accidental_member_steps` migration retires
only the two specifically diagnosed unused appends, with guarded identity/context
assertions. Deployment and repair are owner-run, not automatically applied.

## Redesign boundary

The current legacy `WorkRequest` is Project-only and requires category, attachment category, assigned/origin Division and mutable routing columns. Its generic `Document` parent is also legacy Project-only. V1 does not reuse those structures. A future approved migration must introduce the following target concepts without guessing a backfill from legacy data.

## Aggregate and parent invariant

Target Work Request has UUID `id`, `tenantId`, nullable `bidId`, nullable Project relation ID, `title`, fixed priority domain value, nullable `notes`, `createdByActorId`, `createdAt`, `updatedAt`, and an optional archive lifecycle only when separately approved. Physical Project relation naming follows Module 09’s direct Project redesign (for example, `directProjectId`); API terminology remains `projectId`.

## Archive lifecycle proposal (specification only)

The current route aggregate is `WorkRequestV1`; it has no archive lifecycle fields. The legacy `WorkRequest.deletedAt` belongs to the historical/pre-route aggregate and is technical soft-delete semantics, so it must not be reused for this business archive lifecycle and no second overlapping `deletedAt` flag is introduced.

Future approved persistence is additive on `work_requests_v1` / `WorkRequestV1`: nullable `archivedAt`, nullable `archivedByActorId` (tenant-qualified ActorProfile relation), and nullable `archiveReason`. `archivedAt IS NULL` means active and non-null means archived. A tenant/listing index beginning with `tenant_id, archived_at` is required for the default active filter and explicit lifecycle filter. This proposal requires a future schema/migration/RLS/grant review; this specification creates none.

`WorkRequestV1Event` remains the append-only audit source. Archive writes one `WORK_REQUEST_ARCHIVED` event and restore writes one `WORK_REQUEST_RESTORED` event in the same transaction as the lifecycle-field change. Each carries the Work Request ID through its relation, performer ActorProfile, timestamp, optional archive reason in `note`, correlation/idempotency metadata, and archive-state transition metadata. To preserve the derived workflow state, both events retain the current derived workflow state as their state snapshot; they do not synthesize an archive workflow state or rewrite prior events. No route, assignment, cycle, TeamStep, MemberStep, revision, information, conversation, document, document-version, or audit row is changed by either command.

Future permission-catalogue persistence must add the dedicated global reusable `ARCHIVE_WORK_REQUEST` and `RESTORE_WORK_REQUEST` capabilities, with compatibility determined by the existing Work Request scope-catalogue process. They are not workflow-action aliases and must never be granted by organization-specific names.

`bidId` and `projectId` have tenant-qualified FKs to independent Bid and Direct Project records. A database CHECK requires exactly one non-null parent; service validation mirrors it. Index `(tenant_id, bid_id)` and `(tenant_id, project_id)` support parent detail/list reads. No parent type discriminator, workspace relation, category, legacy code, origin Division, or mutable current-assignment/status column is permitted.

Before creation, a repository validates same tenant, active/readable parent scope, and configured eligible parent state. Parent status is read from its latest parent event; it is not copied into Work Request.

## Fixed priority domain

Work Request stores `priority` directly as a fixed, required domain value: `Low`, `Medium`, or `High`. There is no priority ID, foreign key, reference/master table, CRUD API, lifecycle, seed, or provisioning. API/DTO validation is case-sensitive and rejects every other string. A future Prisma implementation may use an enum whose persisted values are exactly `Low`, `Medium`, and `High`; it must not introduce a priority relation.

## Assignment history

`WorkRequestV1Assignment.level` includes `DIVISION`, `TEAM`, `MEMBER`, `CHECKING`, `APPROVAL`, and `FINAL_REVIEW`. Reviewer levels hold only `memberId`; the active uniqueness rule is one non-replaced/non-unassigned row per request and level. `WorkRequestV1Event.responsibilityLevel` is nullable so historical events remain valid while generic workflow events snapshot the acting responsibility.

Assignment history may join the existing Member relation only for a safe display projection on
member-targeted rows: Member `id` and `name` map to response `assignee.id` and `assignee.label`.
No additional fields, table, relation, Prisma model, or stored assignment data are introduced.

## Phase C1 package, client submission, and decisions

`EXTERNAL_REVIEW` is another member-targeted assignment level. V1 client packages use tenant-owned `WorkRequestV1ClientSubmission` rows with unique `(tenantId, workRequestId, submissionNumber)` and immutable `WorkRequestV1ClientSubmissionItem` rows referencing exact tenant-owned `WorkRequestV1DocumentVersion` IDs. A submitted row is never edited; a resubmission is a new numbered row.

`WorkRequestV1ClientDecision` is tenant-owned, references one submission and the Work Request, records `ACCEPT`, `REJECT`, or `REQUEST_REVISION`, external actor/contact evidence, note, timestamp, correlation/idempotency, and is unique per submission. Events may reference the relevant submission/decision while historical events remain nullable. Tenant-qualified FKs, request/item ownership validation, event idempotency, and serializable writes protect cross-resource access and concurrent decisions.

Target assignment rows are tenant-owned UUID records with Work Request, level (`DIVISION`, `TEAM`, or `MEMBER`), exactly one matching Division/Team/Member target, `assignedByActorId`, `assignedAt`, nullable `unassignedAt`/`replacedAt`, and nullable reason/note. Tenant-qualified FKs apply where supported. A CHECK enforces target/level consistency; partial unique indexes permit at most one active target assignment per Work Request and level.

Division assignment requires active same-tenant Division. Team assignment requires active same-tenant Team belonging to the active assigned Division. Member assignment requires active same-tenant Member in that Team’s Division and active TeamMember membership (`leftAt IS NULL`). Reassignment closes then inserts in one serializable UnitOfWork. History answers responsibility at any time; current routing is the active row(s) projection.

## Events, audit, and information

Append-only Work Request events/audit have tenant, request, configurable action/event identity, nullable prior state, required resulting state where state changes, performer ActorProfile, occurredAt, note/comments, and correlation/idempotency metadata where platform supports it. Index latest reads by `(work_request_id, occurred_at DESC, id DESC)`. `WORK_REQUEST_CREATED`, assignment, submit, approval/rejection, revision, resubmit, reassignment, request-info, and respond-info are conceptual capabilities, not a closed enum.

Current state is latest event state with deterministic ID tie-breaker. A clarification record links request, requester, target/response, message, timestamps, and state-at-request; it does not alter current state absent an explicit configured transition.

The initial event has null prior state, resulting state `CREATED`, performer, occurrence time, and request correlation. Subsequent resulting states are the eight states in the transition matrix. Revision events retain reviewer, requested return level, source state, resulting return state, note, and correlation; no opaque `REVISION_REQUESTED` state may erase where responsibility returned. The event stream is the authoritative audit and state derivation source; any current-state or current-assignment projection is cache-only and transactionally maintained.

## Documents and tenancy

Target Work Request documents follow the independent Bid/Project document shape: tenant-qualified request parent, nullable generic `documentCodeId`, code snapshot where naming/classification needs it, original filename, generated filename when naming inputs exist, immutable protected storage key, MIME, size, uploader, timestamps, and version/classification history. Storage key is generated under the tenant/request namespace; it is never an external URL or caller input. `files[]` are optional. `files[i] ↔ documentCodeIds[i]` whenever code IDs are supplied; no partial mapping. Document code validation is tenant-valid, active, and generic—never module-specific code fields.

Every owned table carries tenant ownership, TenantContext repository predicates, RLS `USING`/`WITH CHECK`, least required grants, and no BYPASSRLS. Cross-tenant parent, organization, document code, file, event, assignment, and actor access is forbidden. RLS remains defense in depth.

## C3 Bid business-cycle compatibility

C3 adds immutable Bid-cycle membership only for Bid-owned Work Requests: a new nullable `bidBusinessCycleId` is populated when `bidId` is populated and remains null when the exclusive DirectProject parent is populated. Its tenant-qualified compound foreign key proves the cycle belongs to the exact Bid. The approved C3 migration baseline explicitly enrolls every currently Bid-owned Work Request of each active/non-archived Bid into that Bid's newly created cycle 1. This deterministic one-time assignment preserves `bidId`, null Project parent, state, history, C1, and C2 data; it is not timestamp inference or reconstructed history. A legacy Bid already archived at baseline receives no such enrollment; when restored, its new first C3 active cycle starts without pre-C3 requests. Bid conversion never changes this parent invariant: historical Bid requests remain Bid-owned, while future Project requests are independently created with the DirectProject parent only.

## Proposed schema change — Work Request responsibility history

**Proposal only:** add a tenant-owned `WorkRequestResponsibilityHistory` (final Prisma/SQL names subject to database-architect review) for exact Team- and Division-level Work Request responsibility. Existing `WorkRequestMemberStep` remains the authoritative Member participation source and is not redesigned. Existing originating responsibility binding remains valid. No schema or migration is created by this contract. Without a persistent actor-to-execution-context fact, a completed Team Lead or prior Division actor can lose legitimate reads, while inferring a former actor from current leadership can incorrectly grant access.

Each history record carries: UUID `id`; required UUID `tenantId`, `workRequestId`, `routeId`, and `actorProfileId`; optional UUID `memberId` only as a consistency-validated snapshot of the actor's Member identity; required responsibility type `TEAM` or `DIVISION`; required `divisionCycleId`; nullable `teamStepId` (required exactly for `TEAM`, forbidden for `DIVISION`); `startedAt` and `endedAt` for a proven responsibility interval; `createdAt`; and provenance identifying the source assignment or conclusively proven historical event. Records must identify the precise actor, request, and cycle/step rather than only a Team, Division, permission, or current title. A historical point-in-time proof may be recorded only with an explicit provenance kind and actual evidence time; unknown interval boundaries must remain unknown, never invented from an event timestamp. Exact physical columns for interval versus point evidence are deferred to implementation design. Point evidence supports historical read eligibility only and never claims current responsibility.

All actor, optional Member, Work Request, route, DivisionCycle, TeamStep and evidence references must be tenant-qualified. Enforce that the route belongs to the Work Request, the cycle to that route, and the TeamStep to the same cycle and route, using composite foreign keys where available and equivalent database-enforced ownership constraints where not. The `TEAM`/`DIVISION` context shape and `endedAt >= startedAt` where both are known are database checks. A supplied Member must match the actor's validated identity, not an independently selectable target. Tenant RLS `USING` and `WITH CHECK`, normal tenant-scoped unit of work, least grants, and no bypass apply to reads and writes.

Index tenant + actor + Work Request for list/detail authorization and tenant + cycle/step + actor for internal-cycle discovery; include history state only as needed by the query. Prevent duplicate evidence and duplicate open records for the same actor and exact execution context, with scoped idempotency/concurrency protection. Do **not** impose a single responsible actor per DivisionCycle: existing valid Division Lead multiplicity and simultaneous legitimate responsibility must remain possible. Team or Division responsibility changes can close an existing interval and insert another in the same transaction; prior rows and their identities remain readable. Permit a controlled one-time close of an open interval, prohibit rewriting its identity/start/evidence or deleting history, and preserve history across completion, forwarding, archive and restore.

At Division activation/assignment, including origin, intermediate and final-review occurrences, and TeamStep activation, write a proven exact actor/context responsibility in the same existing transaction that assigns responsibility. On a supported transfer, close prior responsibility as appropriate and add the successor atomically; on Division return, record an actor only when the existing workflow actually determines that actor, without inventing a single Lead or changing workflow semantics. Completion/forward closes applicable intervals without deleting proof. Idempotent retries and serializable/concurrent operations must not duplicate records. History is a read/collaboration relationship; execution remains governed by the existing current projection, assignment, permission, and workflow-state guards. No new action or recipient relationship is implied.

Backfill must be conservative, tenant-scoped, auditable and idempotent. Only create an interval where its exact actor, execution context and interval facts are established by authoritative persisted evidence. A bound originating actor, genuinely proven current responsibility, or an event whose performer and exact action/context conclusively prove that person's responsibility may support a narrowly scoped fact; an event performer is not automatically the recipient of an activated context. If only an event occurrence proves a historical actor, record only the proven point with its actual event provenance, not fabricated start/end times. Do not use present Team/Division leadership as proof of past responsibility. Ambiguous legacy cases remain unbackfilled and do not acquire access by inference. Deployment/backfill requires a separately approved migration, least-grant/RLS review, and a cutover plan ensuring transactionally recorded future writes before relying on history.

For legacy completion/forward events, accept the performer as responsibility evidence only when the exact action, historical implementation and authorization at that time conclusively prove it; legacy administrator or ambiguous actions are not proof. The originating DivisionLead binding likewise requires a verified mapping to the particular ActorProfile where multiple profiles or later identity changes exist. If an exact current assignee cannot be validated at cutover, fail closed for that historical fact and report the gap. Division responsibility is not necessarily relinquished while its Team or Members execute; close an interval only upon actual end or transfer. Rollout must enable transactionally recorded writes and conservative backfill before new read authorization relies on this history.

### Transactional integration design (implementation pending)

**Selected design: A, a narrow shared transaction-aware responsibility-history port and persistence adapter.** Work Request, Team and Division repositories call the shared boundary with explicit tenant, exact actor identity, request/route/cycle/step and transition facts. The boundary is shared cross-cutting infrastructure/contracts, not an import of one feature module into another; it must not make Team or Division import a Work Request provider or service. The persistence implementation participates only in the caller's already-active `UnitOfWorkService.execute` / `BaseRepository.transaction` transaction. The existing callback receives the tenant-scoped `PrismaTransactionClient` (currently surfaced to repository callbacks as `PrismaExecutor`); the future adapter must require a transaction-only handle or an active fail-closed ambient UoW and never accept/fall back to a root executor, open `$transaction`, or commit independently. Thus a business-write or history-write error rolls back both. Repository layer owns persistence; service/controller layers do not take concrete Prisma clients. Verify the shared boundary against Articles X/XI and tenant-scope assertions before implementation; placing a Work Request feature repository in another feature's imports is forbidden.

Option B, moving all Team/Division mutations into a Work Request orchestrator, would introduce feature-to-feature orchestration or a broad rewrite and is rejected. Option C has no existing transaction-aware domain hook/callback; inventing a generic hook framework is unnecessary. Existing outbox/event consumers are **post-commit**, so they cannot be the sole source of authorization-grade history: a failed consumer after commit would leave missing or stale proof. They remain suitable for notifications or other non-authoritative side effects. No distributed transaction or circular dependency is introduced.

Never use the forwarding performer as proof of the incoming actor. |

These paths can share an ambient transaction through `UnitOfWorkService`; no existing Work Request provider automatically joins Team/Division writes. The shared boundary must explicitly participate in each owning write, including Team clear and Division revoke, rather than assume an outbox consumer runs before commit. Discovering affected active contexts and synchronizing each is part of the future implementation, not a change in which actor is responsible. Exact actor mapping must be validated against existing identity and scope rules at assignment; multiple plausible ActorProfiles or absent authoritative evidence must never be guessed. If no exact actor is established, do not fabricate a history record or silently declare complete historical coverage. A change of identity or leadership must not infer past responsibility from current title.

Assignment opens an `ASSIGNMENT` interval; replacement closes the prior applicable interval exactly once and creates the successor within the same transaction; completion closes only responsibility that truly ends and retains the row. Re-entry or final-review reassignment opens a new period for its exact occurrence/actor. Lock/revalidate the responsibility source and affected TeamStep/DivisionCycle consistently in a deterministic order, use existing workflow guards and serializable conflict retry, and enforce duplicate and conflicting-open constraints in the database. A retry must use a stable operation/idempotency identity, including after a prior interval has closed; do not rely only on in-memory checks or the current open-row index. Current TeamStep/DivisionCycle and route projections remain the sole current-execution authority; history is evidence for authorized historical reads/collaboration only.

**Prepared migration review:** the existing model and migration are directionally suitable but require a **small revision in the same prepared migration before application**. `ASSIGNMENT` currently stores no immutable, tenant/context-qualified source-assignment provenance, and the open-row partial indexes do not make retries of a closed assignment idempotent. Add a validated exact assignment/source or equivalent durable provenance and a stable idempotency/interval uniqueness key; define an actor-specific, tenant/context-safe mapping including the Team's mutable Lead source and fail closed when multiple ActorProfiles cannot be conclusively resolved. For the existing single Team Lead, add database-backed prevention of conflicting simultaneously open TeamStep ownership after verifying actor/profile multiplicity, while retaining per-actor Division constraints to allow multiple valid Division Leads. Review column-level grants, RLS `USING`/`WITH CHECK`, composite context FKs, one-time close rules, serializable race behavior and idempotent retries against a disposable database before application. Empty ambiguous-legacy backfill remains conservative. Neither schema nor migration was modified or applied by this design task.

After all writers and conservative backfill are deployed and verified, the shared Work Request visibility predicate and internal-cycle discovery/detail authorization may consume tenant-qualified exact-actor history alongside non-cancelled MemberStep participation and the existing originating binding. Retain permission, tenant, scope, resource and authorized Division-cycle boundaries; keep the current-state action checks separate and leave the Request Info recipient matrix unchanged. Until then do not enable a reader that assumes history is complete. Live RLS/integrity validation and cutover require separately authorized database work.

### Exact ActorProfile resolution for responsibility history — finalized design

**Existing identity facts.** `User` is the authenticated account; JWT `sub` and `AuthSession.userId` identify that User, not a Member or ActorProfile. A tenant-owned `Member` may link to a User; a tenant-owned `ActorProfile` links a User, Member, and Role. Active tenant UserRole grants and scope compatibility provide the profile's authorization context; a Team Lead assignment identifies `Team.leadMemberId`, and a Division Lead assignment identifies `DivisionLead.memberId`. `WorkRequestTeamStep` references a Team and `WorkRequestDivisionCycle` a route occurrence; neither binds a responsible ActorProfile. The originating route binds a DivisionLead, not an ActorProfile. Current Team/Division assignment DTOs carry Member IDs, not recipient ActorProfile IDs. The initiating request's actor is the performer and is not necessarily the incoming assignee.

The authentication guard resolves an actor per request through the existing `findActiveActor` default/creation ordering and starter-role handling. That is a session authentication selection, not a persisted Work Request responsibility discriminator. `sessionActorSelect` can use one Team grant for its bound Team; an unordered first grant is not sufficient evidence of a unique assignment context. This design does not alter authentication, profile selection, or RBAC behavior.

**Selected option B — unique context-derived profile, fail closed.** At the responsibility assignment/activation boundary and within the same tenant transaction, construct the complete set of *distinct* ActorProfiles that all satisfy: the exact assigned active Member and that Member's linked active User; the same Tenant and Company/resource boundary; an active ActorProfile tied to that exact Member and User; an active Role and active tenant UserRole grant for that User and Role; the compatible `team` or `division` scope, required compatible execution permission(s), and exact Work Request execution context; and the actual assignment relationship being established. For TEAM this includes the target active Team, TeamStep/cycle and any existing Team-bound grant requirement. For DIVISION it includes the exact active DivisionLead record, its Division and the exact DivisionCycle/route occurrence, including origin, intermediate and final review. A grant or title alone is not a Work Request-specific relationship. Role names, `isDefault`, creation order and unordered `take: 1` are not tie-breakers. When multiple Division Leads are legitimately responsible, resolve each Lead/Member independently; do not collapse them into one person.

Exactly one distinct compatible profile: record that profile as the assigned actor. Zero compatible profiles or two or more equally compatible profiles: **reject the responsibility assignment/activation as unresolved or ambiguous before commit**, with a stable conflict response that does not disclose unrelated identities. A role/grant configuration can be corrected so exactly one profile qualifies; an explicit ActorProfile input is not required or introduced by this design. The caller may retry the same transition only after the context is unambiguous. A caller cannot choose an arbitrary profile or supply a permission alone as proof. Automatic next-Team and next-Division transitions perform the same resolution for the actual assignee, not the currently executing/forwarding actor. This is a future fail-closed validation of previously accepted ambiguous cases; it changes no existing runtime now and does not reorder or redesign execution. It does introduce a possible future conflict response, which must be tested and communicated before implementation; it is not a claim of identical acceptance behavior.

The future transaction-aware writer receives the validated `tenantId`, `workRequestId`, `routeId`, exact `actorProfileId`, immutable `sourceMemberId` and `sourceUserId`, `responsibilityType`, `divisionCycleId`, `teamStepId` for TEAM or `sourceDivisionLeadId` for DIVISION, `startedAt`, assignment-source provenance, and stable tenant-scoped `assignmentKey` retry identity. The writer locks/revalidates the relevant Member/User, profile, grant and assignment/context facts in the owning transaction, then writes history with the same transaction; a failure rolls back the assignment. Retry uses the identical profile, context and provenance and must reject a mismatched identity under the same key. The caller must not accept an externally asserted actorProfileId without this resolution. A transfer closes the previous exact period and opens the next in the same transaction; old identity/evidence is never rewritten.

The recorded ActorProfile, Member and User identity snapshots remain historical facts despite later role, Team, Division, default-profile, or profile-active changes. Historical proof is not recomputed from current leadership or the then-current session's first/default profile. Read/collaboration still requires an authenticated active actor, same Tenant, compatible present scope/permission and exact Work Request/resource relationship. A disabled or revoked profile does not itself grant login or bypass present permissions; if authentication later selects a different ActorProfile, do not silently transfer history by current title or email. Access across a changed profile requires a separately approved, verified identity continuity rule; until then fail closed. Revision execution, current responsibility and the Request Info recipient matrix are unchanged.

**Prepared migration review:** the model stores `actorProfileId`, `sourceMemberId`, assignment key and context; its insert trigger checks active profile-to-Member and current Team/Division Lead source. It does **not** establish exact User binding, unique context-compatible profile/grant/scope or the authoritative selection decision. The same unapplied migration/schema must be revised before use: add immutable tenant-qualified source User identity and selection/provenance snapshot (including equivalent identity evidence for any EVENT record permitted for access); validate profile–Member–User linkage and context-compatible active grant in the transaction; enforce immutable snapshots and tenant/context integrity without an FK that forces historical proof to follow a later mutable profile rebind; and make historical read matching reject a profile/user/member rebind. Candidate uniqueness and concurrency must be validated and locked by the writer before insertion, with database constraints where feasible; a trigger checking only current title is insufficient. Existing tenant FKs, RLS, retry key and single-open TeamStep constraints remain subject to live disposable-database verification. Do not apply the migration or enable new readers until these changes and writers are complete.
