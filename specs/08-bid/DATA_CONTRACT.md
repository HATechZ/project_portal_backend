# Data Contract: 08 — Bid

## DATABASE REDESIGN REQUIRED

Current `projects.workspace_type_id`, `bid_details.project_id`, shared Project events, and Project-only document/work-request FKs make Bid a Project subtype. New writes must not retain that model.

`bids` is independent: UUID id/tenant_id/client_id, name, derived project_code, bidding_number, normalized shipment_number, required POL/POD/Cargo/Vessel option IDs, creator, and timestamps. It has no project ID, type, workspace, source channel, origin division, or Bid-level document code. It uses tenant-qualified Client/master/actor FKs and snapshots the POL/POD display inputs, Cargo/Vessel codes, bidding number, project code, and shipment number. `(id, tenant_id)` is unique; `projectCode` is not an identity/uniqueness key.

`bid_statuses` and append-only `bid_status_events` hold tenant, bid, nullable from, required to, changer, reason, occurredAt; index `(bid_id, occurred_at DESC, id DESC)`. At least `BIDDING` exists. Latest event with deterministic ID tie-breaker derives state; no `current_status`.

`bid_documents` and `bid_document_versions` are Bid-specific, not type-discriminated shared business tables. They hold a tenant-qualified Bid FK, General Document Code FK plus immutable code/name snapshots, `originalFileName`, per-version `uploadedFileName`, immutable `generatedFileName`, `storageKey`, MIME, size, uploader, timestamps, and revision/version metadata. Generated names use the selected Document Code name, never the uploaded base filename. `storageKey` is safely generated as `tenants/<tenantId>/bids/<bidId>/documents/<uuid>.<extension>`; it is immutable through reclassification. Generated filename is not identity: version ID/storage key keep versions distinct even when names/revision codes match.

### Cross-module name claim

Use a neutral `business_name_claims` registry, not a shared BidProject domain: `tenant_id`, `normalized_name`, nullable `bid_id`, nullable `project_id`, audit timestamps, tenant-qualified FKs, and a check that exactly one owner FK is populated. A unique `(tenant_id, normalized_name)` is the authoritative concurrency barrier. It has no combined endpoint, lifecycle, status, DTO, service, or type field.

Create generates the independent Bid UUID, inserts the Bid and its claim in one UnitOfWork transaction, and maps the registry unique violation to 409. Rename locks/updates the Bid and its claim in the same transaction; a target occupied by either a Bid or Project is 409. Delete/rollback of a failed create removes the matching claim transactionally. Tenant RLS and repository TenantContext predicates apply to the registry and every Bid table; no BYPASSRLS.

Migration later expands independent tables/RLS/FKs/registry, backfills legacy BID workspace rows/events/files, quarantines unclassifiable records rather than guessing, validates counts/FKs/RLS/latest events/storage keys/name claims, switches reads/writes, then contracts obsolete workspace/type/BidDetail/conversion/outcome/source-channel structures after consumers leave. Work Requests migrate only after their contract.

## C3 additive data freeze

The legacy combined-workspace `BidOutcomeEvent`, `ProjectConversionEvent`, and `ArchivedBidReviewRequest` records are not C3 authority and must not be reused for new independent Bid/DirectProject writes. They remain historical context until their separately governed legacy retirement.

`bid_business_cycles` is append-only: `id`, `tenant_id`, `bid_id`, positive `cycle_number`, nullable `opened_by_actor_id`, `opened_at`, nullable `reopened_from_outcome_id`, and required `opened_by_c3_baseline_migration` defaulting false. Runtime-created/reopened cycles record the acting ActorProfile and false; the deterministic baseline cycle may have no actor and records true rather than inventing one. It has unique `(tenant_id, bid_id, cycle_number)` and unique `(id, tenant_id, bid_id)`, tenant-qualified Bid/Actor FKs, and `RESTRICT` deletion. Cycle 1 is written with a new C3 Bid; restore writes exactly the next cycle and references the immutable rejected outcome that it reopens. No row is updated to represent a new commercial attempt.

`bid_business_outcomes` is append-only: `id`, `tenant_id`, `bid_id`, `business_cycle_id`, outcome code `WON | REJECTED`, `decided_by_actor_id`, `decided_at`, nullable `note`, and the repository-standard correlation/idempotency fields. Its tenant-qualified compound FK requires the referenced cycle to belong to the exact Bid and tenant. There is one outcome per cycle, a tenant-qualified idempotency uniqueness constraint, and a partial unique constraint permitting at most one `WON` outcome per Bid. Bid/Cycle/Actor deletion is `RESTRICT`. A current open cycle is one with no outcome; no mutable outcome/status field is introduced.

`bid_project_conversions` is append-only and is the complete authoritative conversion audit, not a mutable `sourceBidId`: `id`, `tenant_id`, `bid_id`, `direct_project_id`, `business_cycle_id`, `bid_business_outcome_id`, `converted_by_actor_id`, `converted_at`, nullable `note`, and repository-standard correlation/idempotency fields. It has unique `bid_id` (a Bid converts at most once), unique `direct_project_id`, and unique `bid_business_outcome_id`; all tenant-qualified Bid, DirectProject, cycle, outcome, and Actor FKs use `RESTRICT`. A DirectProject made directly has no conversion row. All conversion fields are immutable after insert.

`bid_archived_review_requests` is append-only audit for the existing archived-review capability: `id`, `tenant_id`, `bid_id`, `rejected_outcome_id`, `requested_by_actor_id`, `requested_at`, nullable `note`, and correlation/idempotency fields. It has tenant-qualified FKs to the exact rejected Bid outcome and actor, `RESTRICT` deletion, and tenant idempotency uniqueness. Restore requires an applicable persisted request; repeated requests remain historical rather than being overwritten.

`WorkRequestV1` gains only nullable `bid_business_cycle_id`. New Bid-owned requests must populate it; DirectProject-owned requests must leave it null. A compound FK `(bid_business_cycle_id, tenant_id, bid_id)` references `(id, tenant_id, bid_id)` on `bid_business_cycles`, and a CHECK enforces that it is populated only for a Bid parent. It is immutable after request creation. Add the readiness index `(tenant_id, bid_business_cycle_id, bid_id)`. The sole approved C3 baseline backfill creates cycle 1 for each existing active/non-archived Bid and sets this membership to that cycle for every currently Bid-owned Work Request of that Bid. It preserves `bid_id`, null Project parent, all states/history, C1, and C2 data. It is neither timestamp inference nor reconstructed historical-cycle membership. Existing archived Bids and their Work Requests remain without active C3-cycle membership; a later restore creates an empty first active C3 cycle, so pre-C3 requests cannot satisfy readiness.

All C3 tables use TenantContext predicates, RLS `USING` and `WITH CHECK`, least grants, tenant-qualified references where supported, and no `BYPASSRLS`. The later implementation uses existing append-only audit and transactional-outbox conventions rather than a C3 transport table.

One later additive C3 migration creates these four Bid tables, the nullable Work Request membership column/compound FK/CHECK/index, RLS, and grants. It neither edits historical migrations nor reparents/copies Bid children or documents. Its only historical membership backfill is deterministic: each active/non-archived Bid gets cycle 1 and every currently Bid-owned Work Request is assigned to that exact cycle. It does not set a Project parent, alter Work Request state/history, touch documents, infer timestamps, or reconstruct older cycles. Archived legacy Bids are not enrolled. Converted Project names use the canonical DirectProject code generator plus the derived-name rule, with ordinary normalized name-claim reservation; the source Bid claim is unchanged.
