# Data Contract: 09 — Project

## DATABASE REDESIGN REQUIRED

The current Project requires workspace type, code/origin division and carries BidDetail/source channel/shared events/conversions/outcomes plus Project-only Document/WorkRequest FKs. It cannot serve an independent direct Project.

The Module 09 Project domain is independent: UUID id, tenant_id, client_id, name, required POL/POD/Cargo/Vessel option IDs, normalized shipment_number, backend-derived project_code, creator, and timestamps. It snapshots POL/POD naming values, Cargo/Vessel code values, Shipment Number, and Project Code at creation. Company policy follows Client scope. It uses `(id, tenant_id)` and tenant-qualified Client/master/Actor FKs. No workspace type, Bid relation/detail, source channel, or origin division is permitted. The historical `projects` table remains the combined workspace root until its separately sequenced backfill/contract; the additive implementation is technically named `direct_projects` (and `direct_project_*` dependent tables) so it cannot be mistaken for or coupled to the legacy table. Runtime/API terminology remains Project. `projectCode` is a naming component, not identity or a client-supplied field.

`direct_project_statuses` and append-only `direct_project_status_events` hold tenant, Project, nullable from, required to, changer, reason, occurredAt; index `(direct_project_id, occurred_at DESC, id DESC)`. At least ACTIVE exists. Latest event with deterministic tie-breaker derives state; no mutable status column.

`direct_project_documents` and `direct_project_document_versions` are Project-specific, not a type-discriminated shared business table. They hold a tenant-qualified Project FK, General Document Code FK plus immutable code/name snapshots, `originalFileName`, per-version `uploadedFileName`, immutable generated filename, immutable `storageKey`, MIME, byte size, uploader/timestamps, and revision/version metadata. Generated name is `<ProjectCode>-<CargoCode>-<VesselCode>-<ShipmentNumber>-<DocumentCode>-<RevisionCode> <DocumentName>.<ext>`; Document Name is the code-name snapshot and uploaded filename supplies only the extension. Keys use `tenants/<tenantId>/projects/<projectId>/documents/<uuid>.<extension>`. Permit repeated document codes and generated filenames; version ID/storage key establish storage identity. `direct_project_document_classification_events` preserves reclassification history. Reclassification never recomputes a historical version name.

Use the neutral `business_name_claims` registry defined by Module 08: tenant_id and normalized name are uniquely constrained, with exactly one tenant-qualified Bid, legacy Project, or direct Project owner FK. It is a concurrency/identity registry only, not a shared business module or `type = BID | PROJECT` abstraction. Project create and rename insert/update the direct Project and its claim in one UnitOfWork transaction; cross-module collisions map to 409. Registry and Project tables have TenantContext predicates, app_user RLS `USING`/`WITH CHECK`, least grants, and no BYPASSRLS.

Migration later expands independent tables/RLS/FKs/registry, separately backfills legacy PROJECT workspace rows/events/files/Work Requests, validates counts/FKs/latest events/storage keys/name claims/RLS, switches reads/writes, and contracts combined structures only after consumers leave. Quarantine unclassifiable records/conversion history until an explicit policy; do not discard or guess.
